# Codex Usage Planner

<p> <img src="https://img.shields.io/badge/Codex-Usage%20Planning-111111?style=flat-square" alt="Codex"> <img src="https://img.shields.io/badge/ChatGPT-Compatible-111111?style=flat-square" alt="ChatGPT"> <img src="https://img.shields.io/badge/AI-Coding-111111?style=flat-square" alt="AI Coding"> <img src="https://img.shields.io/badge/Usage-5h%20%2B%20Weekly-111111?style=flat-square" alt="Usage"> </p>

> Узнай стоимость задачи до того, как потратишь лимит.

**Codex Usage Planner** помогает ещё до запуска задачи оценить её сложность и предполагаемый расход AI-лимитов при работе с Codex.

Он отвечает на практические вопросы:

* Какую модель выбрать?
* Какой уровень reasoning использовать?
* Хватит ли оставшегося 5-часового лимита?
* Насколько задача может повлиять на недельный лимит?
* Нужно ли разбить задачу на небольшие итерации?
* Действительно ли нужна более мощная модель?
* Как переписать исходный prompt, чтобы не тратить лимит на лишнюю работу?

Главная идея проекта:

> Использовать самую дешёвую модель и уровень reasoning, которые способны надёжно выполнить задачу.

---

## Зачем нужен этот проект

Большие задачи для AI-разработки могут расходовать намного больше лимита, чем кажется изначально.

Например, запрос:

```text
Переделай Jenkins permissions, Docker-конфигурацию и CI/CD.
Обнови тесты и исправь все найденные проблемы.
```

может заставить агента:

1. прочитать большую часть репозитория;
2. проанализировать архитектуру;
3. изменить несколько подсистем;
4. запустить тесты;
5. исследовать ошибки;
6. внести дополнительные изменения;
7. снова прогнать тесты;
8. повторить цикл несколько раз.

В результате одна слишком широкая задача может съесть значительную часть 5-часового или недельного лимита.

Codex Usage Planner выполняет **preflight-анализ до запуска разработки**.

Он не выполняет саму задачу.

Он показывает, **как лучше её запустить**.

---

## Что оценивает Planner

При оценке учитываются:

* размер репозитория;
* предполагаемое количество файлов;
* количество затрагиваемых подсистем;
* необходимый объём контекста;
* сложность архитектуры;
* сложность debugging;
* запуск тестов;
* изменения CI/CD и инфраструктуры;
* количество циклов `изменение → тест → исправление`;
* использование внешних инструментов;
* предполагаемое количество агентных итераций;
* выбранная модель;
* уровень reasoning.

На выходе получается:

```text
Сложность задачи
      ↓
Риск для 5h
      ↓
Влияние на weekly
      ↓
Рекомендуемая модель
      ↓
Рекомендуемый reasoning
      ↓
Разбивка задачи
      ↓
Оптимизированный prompt
```

## Пример

### Входные данные

```text
5h осталось: 68%
Weekly осталось: 41%

Репозиторий:
https://github.com/example/project

Задача:

Переделать Jenkins так, чтобы каждый ученик видел только свою job.

Требования:
- Jenkins доступен только разрешённым пользователям;
- одновременно могут выполняться максимум 3 build;
- ресурсы сервера ограничены;
- существующие учебные сценарии нельзя сломать;
- обновить и прогнать тесты.
```

### Пример результата

```text
TASK: LARGE

5H:
🟡 RISK
Expected usage: HIGH

WEEK:
🟡 NOTICEABLE
Expected usage: MEDIUM

RECOMMENDED:
Model: Sol
Reasoning: Medium

WHY:
Задача затрагивает permissions, инфраструктуру и тесты.
Лучше не выполнять её одним большим агентным запуском.

SPLIT:

1. Анализ Jenkins permissions → Sol Medium
2. Реализация job isolation → Sol Medium
3. Ограничение concurrency → Terra Medium
4. Обновление тестов → Terra Medium
5. Документация / cleanup → Luna

ESCALATION:
Использовать Astra только если Sol не сможет найти root cause сложной проблемы.

VERDICT:
⚠️ SPLIT FIRST
```

## Как пользоваться

### 1. Посмотреть текущий usage

Скопируй текущую информацию о лимитах.

Например:

```text
5h remaining: 68%
5h reset: 2h 40m

Weekly remaining: 41%
Weekly reset: 3d 12h
```

Если в твоём окружении Codex доступна команда `/status`, можно вставить её результат целиком:

```text
/status
```

---

### 2. Открыть основной prompt

```text
prompts/planning/usage-planner.md
```

---

### 3. Вставить данные

Заполни:

```text
STATUS:

5h remaining:
5h reset:

Weekly remaining:
Weekly reset:

REPOSITORY:

URL:
Branch:

TASK:

[Вставить исходный prompt для Codex]
```

Не нужно заранее улучшать или сокращать исходную задачу.

Вставляй её так, как собирался отправить Codex.

Planner сам должен найти слишком широкий scope и предложить оптимизированную версию.

## Рекомендуемый workflow

Вместо:

```text
Огромная задача
      ↓
Самая мощная модель
      ↓
High reasoning
      ↓
Весь репозиторий
      ↓
Много итераций
      ↓
Лимит закончился
```

лучше:

```text
Исходная задача
      ↓
Codex Usage Planner
      ↓
Оценка scope
      ↓
Разбивка
      ↓
Подходящая модель
      ↓
Подходящий reasoning
      ↓
Фокусированное выполнение
```

---

## Стратегия выбора моделей

Доступные модели со временем могут меняться, поэтому Planner должен ориентироваться не только на конкретные названия, но и на возможности модели.

Общая логика:

| Класс модели | Для чего использовать                                      |
| ------------ | ---------------------------------------------------------- |
| Лёгкая       | Механические изменения, документация, повторяющиеся задачи |
| Стандартная  | Понятные задачи по реализации и локальные тесты            |
| Сильная      | Основная разработка, refactoring и debugging               |
| Максимальная | Сложная архитектура и трудный root-cause analysis          |

Самая мощная модель должна обычно быть **эскалацией**, а не вариантом по умолчанию.

---

## Стратегия reasoning

Используй минимальный уровень reasoning, которого достаточно для надёжного решения задачи.

```text
Low
 ↓
Medium
 ↓
High
```

### Low

Подходит для:

* механических изменений;
* форматирования;
* простой документации;
* очевидных локальных изменений.

### Medium

Подходит для:

* обычной разработки;
* refactoring;
* debugging;
* написания тестов;
* анализа ограниченной части репозитория.

### High

Стоит использовать для:

* сложной архитектуры;
* тяжёлых cross-module задач;
* сложного root-cause analysis;
* ситуаций, где Medium не справился.

## Когда разбивать задачу

Задачу обычно стоит разбить, если внутри одновременно есть несколько разных типов работы.

Например:

```text
Проанализировать архитектуру
+
Изменить авторизацию
+
Переделать инфраструктуру
+
Обновить CI/CD
+
Написать тесты
+
Прогнать regression
```

лучше превратить в:

```text
1. Анализ
2. Авторизация
3. Инфраструктура
4. Тесты
5. Regression
```

Каждая итерация должна по возможности:

* иметь одну основную цель;
* иметь ограниченный scope;
* независимо проверяться;
* иметь понятное условие завершения.

## Оптимизация prompt

Planner может превратить слишком широкий запрос:

```text
Посмотри проект и переделай Jenkins.
Исправь всё, что связано с permissions и тестами.
```

в более экономичный:

```text
Работай только с Jenkins authorization и job visibility.

Сначала исследуй:
- deploy/jenkins/
- docker-compose.yml
- конфигурацию авторизации, связанную с Jenkins
- Jenkins-specific tests

Цель:
Каждый разрешённый пользователь должен видеть только свою job.

Не нужно:
- рефакторить несвязанный application code;
- менять другие сервисы;
- читать весь репозиторий без необходимости.

После реализации:
1. запусти только связанные с Jenkins тесты;
2. исправь ошибки, появившиеся из-за этих изменений;
3. остановись после успешного прохождения этих тестов.

Не выполняй unrelated cleanup.
```

Чем меньше ненужный scope, тем меньше лишнего контекста и повторных агентных итераций.

## История расхода

После выполнения задачи запиши фактический расход в:

```text
history/usage-log.md
```

Например:

```text
| Date | Repository | Task | Model | Reasoning | 5h Before | 5h After | Cost |
|---|---|---|---|---|---:|---:|---:|
| 2026-09-17 | example/project | Jenkins analysis | Sol | Medium | 72% | 66% | 6% |
```

Это важно, потому что реальный расход очень сильно зависит от конкретного workflow.

После накопления истории Planner сможет опираться уже на реальные измерения, например:

```text
Большой Django refactor + Medium reasoning
Обычный фактический расход: 8–13%

Локальное обновление тестов
Обычный фактический расход: 2–4%

Сложный архитектурный анализ
Обычный фактический расход: 15–25%
```

Такие цифры должны появляться только из реальной истории, а не из придуманных предположений.

## Идея проекта

Codex Usage Planner создан не для того, чтобы избегать мощных моделей.

Он нужен для того, чтобы использовать дорогой reasoning **там, где он действительно даёт дополнительную ценность**.

> Сначала спланируй. Трать reasoning там, где он действительно нужен.
